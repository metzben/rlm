RLM Sandbox Harness

A Recursive Language Model that answers questions about inputs far larger than a context window — running entirely inside a hardware-isolated microVM that never sees the API key paying for it.

Concept

The idea: don't read the context — compute over it

A language model with a 1M-token window still can't answer a question about a 50M-character log file — and even inputs that fit degrade the model's attention when most of the content is irrelevant. The Recursive Language Model (RLM) inverts the arrangement: instead of putting the context into the model, it puts the context next to the model, as a plain Python variable named context inside a persistent REPL.

The root model never sees the full input. It sees only metadata — "context is loaded, 19,351 characters" — and it interacts with the data exclusively by writing Python code. It can print(context[:2000]) to learn the structure, run regexes to count things exactly, or split the input into chunks and call llm_call(chunk) — a smaller, cheaper sub-model — to map a semantic question over each piece. Whatever the code prints comes back to the root model, truncated to a fixed size, so the conversation history stays small no matter how large the input is.

Termination is equally literal: the root model finishes by assigning its answer to a REPL variable named Final. The harness probes for that variable after every executed cell. There is no magic token or output format to parse — the answer is just program state.

The second half of this system is containment. The root model writes arbitrary code, and the harness executes it. That is the whole point — and also the reason the harness runs inside a Docker Sandbox: a microVM with its own kernel, deny-by-default networking, and an egress proxy that injects the real Anthropic API key into outbound requests from the host side, so the credential never exists inside the VM at all.

Architecture

Two processes in a box, one key outside it

Four parts matter. The orchestrator (rlm.py) runs the root-model loop. The kernel (kernel.py) is a real child process holding the Python namespace where context, llm_call, and eventually Final live. The REPL wrapper (repl.py) is the pipe between them. And the sandbox wraps all three, with the sbx proxy standing between the VM and the internet.

The crucial property is what the diagram doesn't contain: there is no arrow carrying the real key into the VM. Model-generated code can print(os.environ) all day and see only the literal string proxy-managed. The proxy terminates TLS (the VM trusts the proxy's CA, installed in the system store by the sandbox template), swaps the real key into the x-api-key header, and forwards the request — and it does this identically for the orchestrator's root-model calls and the kernel's recursive llm_call() traffic, because both go to the same domain.

Mechanism

One query, turn by turn

This is Algorithm 1 from the paper, as implemented in RLM.complete(). A real trace from this repo's smoke test appears on the right of each step.

  1. Bootstrap. The harness spawns the kernel, writes the input to a temp file, and loads it inside the kernel as context — via a file, not a string literal, so quotes, backslashes, or NULs in the data can't break the cell. The same bootstrap defines llm_call() with its own Anthropic client. The root model is told only the length: "context is loaded in your REPL (19,351 characters)."
  2. The root model writes code. Its reply must contain fenced ```python blocks; the harness extracts and concatenates them. In the smoke test, turn one was simply print(context[:2000]) — peek at the structure before deciding on a strategy.
  3. The kernel executes the cell. The code runs against the persistent namespace, so variables accumulate across turns like a notebook. Stdout and stderr — including full tracebacks — are captured and returned. An exception is not fatal; the root model sees the traceback and adjusts.
  4. The probe. After every cell, the harness runs a hidden probe asking the kernel, in JSON, whether Final exists. Not set → the captured output, truncated to 4,000 characters, is appended to the conversation and the loop continues (up to 20 turns).
  5. Termination. The root model assigns Final = "…". The probe sees it, the loop returns the value, the kernel is torn down. In the smoke test this took three cells: peek, Counter(re.findall(...)), assign — an exact answer over data the model never "read."

A reply with no code block gets a nudge ("write code, or assign Final") rather than an error — a cheap recovery that showed up in the very first live run. And because the probe checks state rather than parsing model text for a magic tag, false terminations are structurally impossible: the loop ends exactly when the variable exists.

Recursion depth here is 1, the paper's default: llm_call() is a plain sub-model call, not a nested RLM. Depth > 1 — a sub-call that spawns its own kernel — is a contained change to the bootstrap code, which is an overridable field (subcall_bootstrap) precisely so tests can stub it out and future work can swap it.

Code tour

The components, and why each exists

rlm/rlm.py The orchestrator: system prompt, root-model calls, code extraction, the turn loop, the Final probe. Takes an anthropic.Anthropic client as a constructor argument rather than creating one — so tests inject a mock and the whole loop runs offline against a real kernel with fake models.
rlm/kernel.py A ~50-line stateful REPL: read code from stdin until a sentinel line, exec() it against a persistent dict, print captured output, print the sentinel, repeat. Deliberately minimal — no IPC framework, no jupyter. A line-oriented sentinel protocol (___END_OF_EXEC___) over plain pipes is easy to reason about and easy to sandbox. It catches BaseException, so even model code calling sys.exit() just produces a traceback instead of killing the kernel.
rlm/repl.py SubprocessREPL: spawns the kernel, writes cells, reads until the sentinel. Also home of kernel_env(). This is the only place the kernel's environment is defined. The child gets an explicit allow-list, never the parent's full environment — hygiene for model-run code, and the single spot where the proxy variables that must be forwarded are enumerated.
rlm/cli.py rlm --context FILE --query "…" — argument parsing, file reading, exit codes. Doubles as the sandbox kit's entrypoint. The workspace is mounted at the same absolute path inside the VM as on the host, so a host path passed to --context works unchanged inside.
kit/spec.yaml The Docker Sandboxes kit: image, entrypoint, resources, network allow-list, credential declaration. Declarative security boundary — see the sandbox kit.
Dockerfile Sandbox image: the shell-docker template + Python + this package in a venv. The template provides what kits require (an agent user, proxy-env plumbing, the proxy CA in the system store). Two env vars point Python's HTTP stack at that system CA store — without them, httpx would use certifi's bundle and reject the proxy's TLS interception. Crucially it sets no ENTRYPOINT (see field notes).
tests/test_rlm.py Nine offline tests: real kernel subprocess, mocked models. They pin the behaviors that matter: Final terminates, sub-calls round-trip, output truncates, exceptions surface, secrets don't leak into the kernel env, proxy vars do.
Makefile The operator's interface: venv, tests, image build/push, secret setup, sandbox runs. Docker Sandboxes' CLI surface is still moving; keeping every sbx invocation in one file means one place to fix when a flag changes.

Security model

Where the key lives — and where it can't reach

The threat model is specific: the root model writes arbitrary code, and this harness executes it. Prompt-injected context, a jailbroken model, or an honest mistake all reduce to the same thing — untrusted Python running with network access. The design answers with three nested layers:

What the sandbox gives you

  • Hypervisor isolation — the harness runs on its own kernel in a microVM, not in a shared-kernel container on the host.
  • Deny-by-default egress — the global policy denies everything; the kit allows exactly api.anthropic.com:443. Exfiltration has nowhere to go.
  • Proxy-managed credentials — the real key stays in the macOS Keychain. Both VM processes see the placeholder proxy-managed; the host proxy injects the real header on the way out.

What it deliberately doesn't

  • No isolation between the two VM processes. Orchestrator and kernel share a filesystem and network namespace. Acceptable here because the one secret worth stealing isn't in the VM to steal.
  • make local-run is trusted-input only. Outside the sandbox the key is real and does reach the kernel — it has to, for llm_call. Development convenience, not a safe mode.

Even inside the VM, the kernel doesn't inherit the orchestrator's environment. kernel_env() builds an explicit allow-list — the necessities, the proxy plumbing, and the credential variable that is, by design, worthless in there:

# repl.py — the kernel's entire environment, enumerated
PATH  HOME  LANG  LC_ALL  TMPDIR          # basics
HTTP_PROXY  HTTPS_PROXY  NO_PROXY  (+lowercase)  # route llm_call via the proxy
SSL_CERT_FILE  REQUESTS_CA_BUNDLE          # trust the proxy's TLS interception
ANTHROPIC_API_KEY  ANTHROPIC_BASE_URL      # inside the VM: "proxy-managed"

Two tests keep this honest: one plants SUPER_SECRET_TOKEN in the parent environment and asserts the kernel can't see it; another asserts HTTPS_PROXY does arrive. The allow-list can't silently rot in either direction.

Verified live: during the first sandboxed runs, both API paths worked while the VM held only the placeholder — the root loop answered an exact counting query via regex, and a second run exercised llm_call() fan-out through the proxy. The key never left the host.

Configuration

The sandbox kit: the boundary, declared

kit/spec.yaml (schema v2) is where the security story stops being convention and becomes configuration the runtime enforces. Three stanzas do the work:

# the image is a kit argument, so the Makefile passes the tag it just pushed
sandbox:
  image: "${{ kit.args.image }}"
  entrypoint: ["/home/agent/.venv/bin/rlm"]   # launched INSIDE the running container

permissions:
  network:
    allow:
      - "api.anthropic.com:443"              # the entire allow-list

credentials:
  - service: anthropic
    required: true
    apiKey:
      name: ANTHROPIC_API_KEY
      proxyManaged: true                    # VM sees a placeholder, never the key
      inject:
        - domain: api.anthropic.com
          header: x-api-key

The credential references a service name (anthropic), not a value. The value is stored once on the host with sbx secret set anthropic and bound to this kit on first run via an explicit approval prompt — the binding is remembered in the sbx config, so subsequent runs (including detached ones) need no interaction. proxyManaged: true is the single line that flips the whole credential model from "env var in the container" to "header rewrite at the proxy."

One operational consequence of the architecture: the sandbox VM runs its own private Docker engine, which pulls the kit image itself. A host-local image is invisible to it — the image must live in a registry the VM can reach (this project pushes to Docker Hub).

Operations

Running it

# one-time setup
brew install docker/tap/sbx        # Docker Sandboxes CLI
sbx login                          # sandboxes require a Docker sign-in
sbx policy init deny-all           # global egress baseline; the kit allows on top
make secret                        # store the Anthropic key host-side (prompts)
make venv test                     # 9 offline tests — no API calls, no key needed
make build push                    # build the image, push so the VM can pull it

# the loop you actually use
make run CONTEXT=./big.log QUERY="How many distinct error codes appear?"

# housekeeping
make status                        # list sandboxes (sbx tui for a live dashboard)
make rm                            # delete the sandbox VM
make local-run CONTEXT=… QUERY=…   # DEV ONLY: no sandbox, real key reaches the kernel

Useful knobs on the CLI: --root-model / --sub-model (defaults: Sonnet for the root, Haiku for sub-calls — the root model needs judgment, the mapped calls need volume), --max-turns (default 20), and --quiet to print only the final answer. Extra flags pass through make run via RLM_ARGS="…".

Hard-won specifics

Field notes from the first live runs

Docker Sandboxes and kits are experimental; these are the things that actually bit during bring-up, recorded so they don't bite twice.

  • Never set an ENTRYPOINT in the image. The sandbox runtime needs the template's own init (tini) as the container's main process: it keeps the container alive while the runtime injects a start-agent helper, which then launches the kit's declared entrypoint. Overriding the entrypoint with rlm made the container exit at birth — surfacing only as the cryptic started hook: … container is not running.
  • The kit is a positional argument. sbx run ./kit <workspace> -- <args> — the --kit flag exists but means "mixin on a built-in agent," which is a different thing.
  • Local images don't reach the VM. The sandbox's private engine pulls from registries only; a host-only tag fails with a bare 403. Push first.
  • The global network policy must be initialized once (sbx policy init) before any sandbox starts. deny-all is the baseline that matches this project's promise; per-kit allows layer on top.
  • The credential binding is approved interactively, once. A non-interactive first run doesn't prompt — it warns and starts the sandbox without the credential. Do the first make run in a terminal you're watching.
  • There is no sbx logs. Use sbx ls / sbx tui; the daemon's own log lives under ~/Library/Application Support/com.docker.sandboxes/…/daemon.log and is where the real container-start errors surface.
  • Exact counting belongs to code, semantic reading to sub-calls. In live runs, the root model's regex counted error codes perfectly; a forced llm_call-per-chunk strategy produced plausible but fuzzy counts. That division of labor is the RLM thesis in miniature — let the model choose code when precision matters.
